LATAR BELAKANG MASALAH

Pengelolaan Rapor Manual & Risk Data Corrupt

Pengelolaan rapor di SMK Nangkaleah masih manual menggunakan Microsoft Excel dan serah terima dokumen fisik, memicu kesalahan perhitungan (human error) dan risiko kehilangan/kerusakan data.

"Risiko file corrupt sangat tinggi karena pertukaran data nilai masih mengandalkan flashdisk antar guru mapel dan wali kelas."

Sandi Supriadi — Kaprog PPLG

Dampak Operasional

  • Guru Mapel: Membutuhkan 1–2 hari penuh hanya untuk memverifikasi dan merekap nilai kelas.
  • Wali Kelas: Membutuhkan waktu berminggu-minggu menggabungkan data dari berbagai file Excel.
  • Orang Tua & Siswa: Tidak memiliki akses langsung untuk memantau perkembangan nilai secara real-time; rapor hanya dibagikan dalam bentuk cetak fisik.

TUJUAN PENELITIAN

Target Solusi yang Dihasilkan

Pencapaian konkret yang dirancang untuk menjawab secara langsung setiap poin rumusan masalah.

Tujuan 1

Menghasilkan dan merancang bangun Sistem Informasi Rapor Digital berbasis website di SMK Nangkaleah menggunakan metode Waterfall yang mampu mengotomatisasi pengolahan nilai dan mendistribusikan laporan secara real-time, serta meminimalkan resiko hilangnya data akibat pertukaran fisik melalui penyimpanan data secara digital dan terpusat..

Tujuan 2

Menghasilkan fitur notifikasi berbasis WhatsApp pada sistem yang memungkinkan wali kelas mengirimkan pemberitahuan rapor kepada orang tua/wali secara individual per siswa melalui tombol "Send Notif" pada setiap data siswa. "Send Notif" untuk pengiriman nilai secara privat oleh wali kelas.

Tujuan 3

Mengevaluasi kelayakan sistem informasi yang dibangun melalui pengujian komprehensif berdasarkan standar kualitas perangkat lunak ISO/IEC 25010:2023 pada aspek Functional Suitability, Usability, Portability, dan Security.

BATASAN PENELITIAN

Ruang Lingkup & Batasan Sistem

Penetapan batasan operasional agar pengembangan sistem tetap terarah dan fokus pada kebutuhan mendesak sekolah.

  • 01 / Arsitektur

    Sistem yang dirancang berbasis website dan difokuskan pada digitalisasi penginputan, pengolahan, penyimpanan, hingga penyajian laporan akademik.

    Evaluasi kelayakan produk perangkat lunak diukur secara eksklusif menggunakan parameter Functional Suitability, Usability, Portability, dan Security.

    Pengembangan metode Waterfall hanya sampai pada tahap pengujian (Testing) dan tidak mencakup tahap Maintenance.

B2 · ARSITEKTUR BACKEND

Supabase & Row Level Security

Pola arsitektur Backend-as-a-Service (BaaS) berbasis PostgreSQL dengan autentikasi JWT bawaan dan kebijakan proteksi data di tingkat database (RLS).

Database Engine: PostgreSQL 15 dengan ekstensi PostgREST.
Auth Service: Supabase Auth (JWT bearer token).
Security Enforcement: Row Level Security (RLS) di level tabel.

Alur Autentikasi & Otorisasi Data

1. Login

Pengguna menginput credential → Supabase Auth menerbitkan JWT token yang berisi sub (user_id) dan role.

2. Request

Frontend React mengirim REST API request dengan header Authorization Bearer JWT.

3. Evaluation

PostgreSQL mengevaluasi klausa USING pada kebijakan RLS sebelum mengembalikan query data.

B6 · SECURITY VULNERABILITY

Detail Celah Keamanan RLS Tabel users

Temuan celah Confidentiality pada kebijakan awal Row Level Security (RLS) yang menyebabkan pass rate awal hanya 75%.

Penyebab Masalah: Kebijakan RLS awal memakai klausa auth.role() = 'authenticated' tanpa mengecek keterikatan auth.uid() = id. Akibatnya, akun siswa dapat membaca seluruh 109 baris data pengguna lain.

Kode SQL Policy Bermasalah (Sebelum Perbaikan)

schema_vulnerability_before.sql ❌ Pass Rate Security: 75% 
-- Kebijakan RLS yang bermasalah (Sebelum Perbaikan):
CREATE POLICY "Enable read access for authenticated users" 
ON public.users 
FOR SELECT 
TO authenticated 
USING (
  auth.role() = 'authenticated'
);
B7 · PERBAIKAN SECURITY RLS

Kebijakan RLS Setelah Perbaikan

Perbaikan Row Level Security untuk menjamin privasi data antar role (pass rate naik menjadi 100%).

100% Pass Rate Pengujian Keamanan (4/4 Skenario)

Kode SQL Perbaikan RLS

schema_security_patch.sql ✓ Pass Rate Security: 100% 
-- 1. Hapus policy yang bermasalah
drop policy "users_select_own_or_staff" on public.users;

-- 2. Buat fungsi helper yang bypass RLS saat mengecek role
create or replace function public.get_my_role()
returns text
language sql
security definer
set search_path = public
stable
as $$
  select role from public.users where id = auth.uid()
$$;

-- 3. Buat ulang policy pakai fungsi tersebut (bukan subquery langsung ke tabel users)
create policy "users_select_own_or_staff"
on public.users
for select
using (
  auth.uid() = id
  or public.get_my_role() in ('TU', 'KEPALA_SEKOLAH')
);
